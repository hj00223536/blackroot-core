# BLACKROOT external trust-witness protocol proposal

**Status: DESIGN PROPOSAL ONLY. No witness service, witness key, quorum, endpoint, release policy, or anti-rollback authority is configured or approved. This document does not authorize trust activation, Genesis issuance, BRT issuance, Testnet, or Mainnet.**

## 1. Purpose and security boundary

A local SQLite checkpoint can detect a stale database only when the node has an independently obtained current sequence and digest. Restoring both the database and every local copy of the expected values defeats a local-only check.

An external witness is intended to provide independently administered, freshness-verifiable evidence of the latest accepted trust-policy checkpoint. The witness is not a Genesis approver and must not sign manifests, founder allocations, or launch decisions.

The protocol must not treat a valid signature as proof of freshness by itself. A signed old response can be replayed unless the request and response are bound to a fresh challenge and the witness enforces monotonic state.

## 2. Roles and separation

Keep these roles separate:

- **Owner governance:** approves trust-policy changes and witness membership through an independently documented process.
- **Trust-policy signer:** signs a specific trust configuration under its narrowly scoped authority.
- **Witness operator:** independently stores the highest accepted checkpoint and signs freshness-bound attestations. A witness must not be able to create a trust-policy update merely by witnessing it.
- **Node verifier:** validates witness identity, signature, challenge, network, sequence, digest, predecessor, and quorum policy before enabling trust-dependent operations.
- **Release authority:** makes a separate human decision for any launch or issuance. Witness quorum is not launch approval.

Witness operators, signing keys, infrastructure, backups, and administrative credentials must not all share one control plane. Independence must be demonstrated operationally, not inferred from different key IDs.

## 3. Checkpoint identity

A checkpoint statement must bind at least:

- protocol and schema version;
- immutable project identifier;
- exact network identifier;
- trust-configuration sequence;
- exact trust-configuration digest;
- exact predecessor digest (absent only for the explicitly approved initial sequence);
- policy epoch or governance decision identifier;
- witness-set identifier and witness-set version.

The witness must validate the trust configuration and its owner-governance authorization before advancing its stored checkpoint. It must reject same-sequence/different-digest conflicts, sequence gaps, wrong predecessors, cross-project/network statements, revoked signers, and unrecognized policy versions.

The checkpoint is not a free-form string. Its exact encoding, field lengths, integer ranges, domain separation, and test vectors must be specified and independently reviewed before implementation. Do not assume the repository's current restricted JSON canonicalizer is a finalized cross-language signing format.

## 4. Fresh challenge and signed response

A node creates a cryptographically random challenge nonce for each verification attempt. The nonce must be generated by an operating-system CSPRNG, have a fixed reviewed length, be single-use, and never be reused after restart. A timestamp alone is not a substitute for a nonce.

The node sends the witness:
- protocol version;
- project and network identifiers;
- fresh request nonce;
- the node's locally stored checkpoint, if any (as a comparison hint only).

The witness reads its authoritative monotonic checkpoint and returns a signed statement binding:
- the exact request nonce;
- project and network identifiers;
- witness identity and witness-set version;
- current sequence, digest, and predecessor;
- a monotonically increasing witness-local log index or equivalent durable revision;
- response issue time and a short expiry, if trusted time is available;
- protocol version and signature algorithm identifier.

The signature must cover an unambiguous, domain-separated encoding of every field. The signature algorithm, canonical encoding, nonce length, time rules, expiry bounds, and test vectors must be frozen before code is written. Never sign a concatenated string without a length-delimited encoding.

The node rejects a response if the nonce differs, has already been consumed, the witness identity is not pinned for the current witness-set version, the signature fails, the project/network differs, fields are malformed, the response is expired under a trusted-time policy, or the checkpoint conflicts with the approved policy.

A fresh nonce prevents replay of an old response to a new challenge only if the witness signs the exact challenge after reading its current durable state. It does not protect against a compromised witness that lies about its state.

## 5. Witness monotonic storage

Each witness must persist its own accepted checkpoint before acknowledging an update. The update operation must be atomic and serialized across all witness processes and hosts that share that witness identity.

Required transitions:

1. Initial enrollment is accepted only through an out-of-band approved bootstrap procedure.
2. A later checkpoint advances by exactly one sequence and names the exact currently stored digest as predecessor, unless governance explicitly approves a separately specified recovery transition.
3. Same sequence and same digest may be treated as an idempotent retry.
4. Same sequence with a different digest is a hard conflict and must be escalated.
5. Lower sequence, skipped sequence, wrong predecessor, wrong network, or unauthorized signer is rejected.
6. The witness must commit durable state before returning a signed success response.
7. Corruption, missing state, restore detection, or uncertain durability stops signing; it must not silently initialize from a client request or local backup.

A witness's local database is not sufficient against an operator who can restore its entire state. Witness deployments therefore need independent backup/restore controls and externally auditable monotonic evidence. A transparency log, hardware monotonic counter, or separately administered checkpoint channel are candidate mechanisms, not selected solutions.

## 6. Quorum and witness-set governance

A single witness is a single point of compromise and availability failure. A quorum can reduce this risk only if operators are genuinely independent and the membership/threshold policy is authenticated.

Before implementation, governance must explicitly select:
- witness count and threshold;
- operator independence requirements;
- witness public-key enrollment and rotation;
- revocation and compromise response;
- outage and partition behavior;
- quorum changes and their approval threshold;
- recovery when fewer than the required witnesses are available.

Do not hardcode an unapproved threshold such as 2-of-3. A node must not lower the threshold or fall back to one witness because others are unavailable. If the approved quorum cannot be reached, trust-dependent operations remain disabled.

## 7. Freshness, equivocation, and transparency

A witness can sign two conflicting statements. The protocol must preserve signed responses as evidence and detect equivocation when different digests are observed for the same project, network, sequence, and witness-set version.

A future transparency layer should provide independently verifiable append-only inclusion and consistency proofs, with externally witnessed tree heads or equivalent checkpoints. A signed tree head without independent consistency/freshness checking is not enough.

Trusted time is an operational dependency, not a replacement for sequence monotonicity. If expiry is used, define trusted-time sources, maximum clock skew, outage behavior, and recovery. If time cannot be trusted, reject time-dependent freshness claims rather than silently extending expiry.

## 8. Node verification algorithm

Before trust-dependent startup:

1. Acquire the mandatory node data-directory lock.
2. Generate a fresh single-use challenge.
3. Query the configured witness set over authenticated transport.
4. Verify each response signature and exact challenge binding.
5. Verify witness-set version, membership, revocation, project, and network.
6. Verify checkpoint sequence, digest, predecessor, and governance authorization against the separately pinned release policy.
7. Enforce the approved quorum and conflict/equivocation rules.
8. Compare the verified external checkpoint with local persistent state.
9. If local state is older, newer, conflicting, corrupt, or missing unexpectedly, stop and require a separately authorized recovery procedure. Do not auto-repair from a witness response.
10. Only after a reviewed acceptance transition may the node expose the specific trust-dependent capability.

The witness response is evidence for comparison; it is not by itself an issuance token or permission to create Genesis outputs.

## 9. Failure and recovery rules

Fail closed on:
- unavailable or insufficient witnesses;
- stale, malformed, expired, or replayed response;
- invalid signature or unknown/revoked witness;
- witness-set version mismatch;
- conflicting statements or detected equivocation;
- sequence downgrade, gap, or predecessor mismatch;
- policy signer or governance authorization failure;
- local state rollback, corruption, or unexplained absence;
- uncertain witness durability or restore status.

Recovery must use an independently authenticated governance decision, preserve old signed evidence, document the reason and affected sequence range, and require independent review. Never reset sequence numbers, replace witness keys, or accept an older checkpoint merely to restore availability.

## 10. Security and operational tests

Before implementation acceptance, add independent test vectors and adversarial tests for:
- challenge nonce replay, reuse, truncation, and cross-network substitution;
- response signature mutation and field omission/duplication;
- expired responses and trusted-clock failure;
- same-sequence equivocation by one witness;
- conflicting responses across a quorum;
- witness database snapshot restore while an external checkpoint remains newer;
- witness crash before commit, after commit, and before response;
- concurrent witness writers and split-brain deployment;
- witness key rotation, revocation, and compromise;
- quorum loss, network partition, and recovery;
- malformed encodings, integer overflow, and unknown protocol versions;
- independent cross-language verification of every signed byte vector.

A mock witness or unit test with a hardcoded public key is not evidence of production witness independence or key custody.

## 11. Deployment and privacy requirements

Do not publish a witness endpoint, expose a public listener, or collect node-identifying telemetry until the threat model, network controls, privacy impact, abuse controls, incident response, and operational ownership are reviewed. Witness responses should reveal only the minimum checkpoint metadata required; do not include wallet data, private keys, user identifiers, or transaction history.

## 12. Stop conditions

Until the witness protocol, membership, quorum, key custody, external monotonic evidence, recovery process, implementation, adversarial tests, and independent review are complete:

- no real witness key or owner key is to be added to the repository;
- no local checkpoint is to be described as rollback-proof;
- no trust-witness response is to authorize Genesis issuance;
- no founder allocation or production issuance state is to be initialized;
- no public Testnet or Mainnet launch is authorized.

## 13. Relationship to existing repository work

The current `TrustCheckpointStore` is a local SQLite checkpoint. It supports local sequence/predecessor checks and can compare its contents with externally supplied expected values. It cannot authenticate those values, provide a fresh challenge-response, enforce an independent quorum, or prevent restoration of the witness's own database.

The existing trust validator accepts caller-supplied external pins. The genesis authorization composition verifies a manifest, trust configuration, and detached approval against supplied pins, but does not authenticate the provenance or freshness of those pins.

This proposal is a protocol design only. It deliberately adds no network service, key, endpoint, quorum, startup integration, or issuance capability.
