# Browser wallet implementation contract

Status: implementation specification; not a production wallet.

## Scope

The first release is a single-account legacy P2PKH wallet for the BLACKROOT test network only. It must not advertise mainnet support until network identity, consensus, genesis, node RPC and independent review are complete.

## Key generation and signing requirements

- Use a maintained, independently reviewed secp256k1 implementation with reproducible, pinned dependencies. Do not implement elliptic-curve arithmetic, ECDSA, deterministic nonce generation, or signature parsing in application JavaScript.
- Generate private-key entropy with browser Web Crypto crypto.getRandomValues only in a secure context.
- Derive compressed public keys and signatures with the reviewed secp256k1 library.
- Keep private key material in memory only for the active session; clear references on lock/logout where practical.
- Never send private keys, seeds, passphrases, or decrypted vault data to an API, analytics, crash reporter, browser console, GitHub, or support channel.
- Never put secrets in URL parameters, localStorage, sessionStorage, IndexedDB plaintext, logs, or clipboard automatically.
- Do not add remote scripts, third-party analytics, advertising, or remotely hosted wallet dependencies to the wallet origin.
- Require a strong user passphrase to encrypt an exported backup. Use Web Crypto PBKDF2-HMAC-SHA-256 with a high, benchmarked iteration count and AES-256-GCM with a fresh random 96-bit nonce. Store only versioned ciphertext, salt, nonce and KDF parameters in the exported file.
- Explain clearly that browser storage is not a substitute for an offline backup. Offer encrypted file export only after independent review and user confirmation.
- Do not implement seed phrase import/export in the first release.

## Address rules

- Address version must come from a frozen network configuration, never from a hard-coded guess.
- P2PKH payload must be exactly 20 bytes; checksum and version must be validated before display/use.
- The current 0x26 value in docs/network-identity-proposal.md is provisional and must not be used to receive real funds.
- Add independent test vectors generated by a second implementation before enabling receive addresses.

## Transaction rules

- Build and sign transactions only after the node API, fee policy, UTXO selection, change handling, locktime, sequence and replay-protection rules are specified.
- Display destination, amount, fee and change separately and require explicit confirmation.
- Reject unknown scripts, unsupported sighash flags, malformed transactions and unexpected network identifiers.
- Do not broadcast until the user confirms the exact transaction summary.

## Release gates

1. Freeze and independently review network identity and genesis.
2. Add audited/pinned crypto dependency and reproducible build.
3. Add browser tests for key generation, address vectors, encryption/decryption, wrong-password rejection, tamper detection and secret non-disclosure.
4. Add transaction construction/signature verification vectors shared with the node implementation.
5. Add CSP, dependency audit, static analysis and security review.
6. Run a public testnet with no real-value claims before mainnet consideration.

## Current truthful status

The repository currently has address encoding/decoding helpers and unit tests, but no production browser key manager, encrypted vault, transaction signer, or production network. This document does not create keys, funds, or activate a chain.
